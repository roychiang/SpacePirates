## 目標與範圍
- 建立多人功能的專案管理流程，以現有 UI 風格與已定 PRD/架構為準，確保按期交付：Auth/Avatar、配對與大廳、遠端雙人 NetSync、結果頁與 E2E 測試。
- 全程遵守：非重導登入、圓形頭像與預設圖、VIVERSE SDK 對接、viverse.com 上線驗證。

## 管理節奏
- 每日更新：進度/阻塞/風險簡報（≤5條），含里程碑燃盡。
- 每週節點：里程碑評審與計劃滾動，確認下一週交付物。
- 變更同步：需求變更即時評估影響，當日更新文檔並回報時程。

## 看板工作流
- 欄位：Backlog → In Progress → Review → Done；限制同時進行最多 1–2 項高優先工作。
- 任務標準：動詞開頭、原子（≤14字）、與使用者語言一致；包含清晰輸出與驗收。
- 標籤：`Auth`、`Avatar`、`Play`、`UI`、`NetSync`、`Test`、`Docs`、`Perf`、`Risk`。
- 完成定義（DoD）：
  - 功能可運作（本地 Stub 或 viverse.com 實測）
  - 文檔更新（PRD/架構/規格）
  - 驗收與測試案例通過（含邊界）
  - 無重大性能回退（FPS/延遲門檻達標）

## 里程碑（與交付物）
- M1（週1）：PRD 與 UI 規格定稿；服務契約摘要；配對/大廳原型草稿。
- M2（週2）：Auth/Avatar 整合與主頁狀態（`checkAuth`/`getToken`/`getProfile` + 圓形頭像/guest）。
- M3（週3–4）：配對頁與 Play SDK 對接（`newMatchmakingClient`、`setActor`、`createRoom/joinRoom`、QueuePanel/RoomJoinForm）。
- M4（週5–6）：大廳與準備機制（`getMyRoomActors`、房主開始/關閉、玩家列表與準備勾）。
- M5（週7–8）：遠端雙人 NetSync（輸入同步、狀態增量、預測/權威修正、斷線重連）。
- M6（週9）：結果頁與再玩一次；流程收斂。
- M7（週10）：viverse.com E2E 測試與修正（登入/房間/準備/遊戲/結果/重試）。
- M8（週11）：性能優化、錯誤處理完善、監控與日誌、最終驗收。

## 驗收與度量
- 功能驗收：依 `multiplayer_product_requirements.md` 第16章與各頁面規格（第19章）。
- 測試策略：
  - 本地 Stub：`checkAuth`/`getProfile`/`newMatchmakingClient` 模擬成功與錯誤；驗邊界（憑證失效、滿員、斷線、超時）。
  - E2E（viverse.com）：完整流程與限定場景；無重導登入。
- 度量：
  - 速度：每週完成任務數（吞吐）、里程碑燃盡率
  - 品質：缺陷數/重開率、邊界用例通過率
  - 性能：FPS≥60（最低30）、延遲≤100ms（可接受≤200ms）、重連≤5s

## 風險與緩解
- SDK 測試受限：本地 Stub 先行，E2E 在 viverse.com 驗證；接口封裝以應對變更。
- 非重導登入限制：堅持 `checkAuth()` 被動檢查；guest 降級呈現；錯誤回饋清晰。
- NetSync 難度：優先雙人拓撲、輸入驅動與增量同步；提供調試參數以適配延遲。
